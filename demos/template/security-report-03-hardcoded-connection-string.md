### Code Snippet

```csharp
const string connectionString = "Data Source=localhost;Initial Catalog=TestDB;Integrated Security=true;";
```

### Problem Description

The database connection string is hardcoded as a compile-time `const` in the source file. Even though this particular string uses `Integrated Security=true` rather than an embedded SQL password, embedding connection configuration in source is a security and operational weakness:

- **Disclosure**: the connection details (server, database name, auth mode) are baked into the compiled binary and committed to source control, exposing infrastructure details to anyone with repository or assembly access. If this pattern is followed for other environments, a SQL username/password would end up checked into the repo permanently (and in git history even after removal).
- **No per-environment configuration**: the same string is used everywhere, encouraging copy-paste of production secrets and making credential rotation require a code change and redeploy.
- **Reconnaissance value**: server name and database name aid an attacker who has gained any foothold (e.g. via the SQL injection in the companion report) in pivoting and targeting.

Severity is Medium here because no plaintext SQL password is present and exploitation requires access to the source/binary; it would rise to High/Critical if a SQL password were embedded.

## 🛠️ Remediation

### Fixed Code

```csharp
var builder = WebApplication.CreateBuilder(args);

// Read from configuration providers (appsettings.json, environment variables,
// user-secrets in dev, or a secrets manager / Key Vault in production).
var connectionString = builder.Configuration.GetConnectionString("TestDB")
    ?? throw new InvalidOperationException("Connection string 'TestDB' is not configured.");

var app = builder.Build();

app.MapPost("/login", (string email, string password) =>
{
    using var connection = new SqlConnection(connectionString);
    // ...
});
```

With the secret supplied outside source control, e.g. an environment variable:

```
ConnectionStrings__TestDB=Data Source=...;Initial Catalog=TestDB;Integrated Security=true;
```

### Fix Explanation

The connection string is moved out of source into the configuration system. In development it can come from user-secrets or `appsettings.Development.json`; in production it should come from environment variables or a dedicated secrets store (Azure Key Vault, AWS Secrets Manager, HashiCorp Vault). The source no longer contains infrastructure details or any credential, secrets can be rotated without recompiling, and each environment supplies its own value. A null-check fails fast with a clear error if the configuration is missing.

### Prevention Best Practices

- Never hardcode connection strings, API keys, or credentials in source. Use the configuration system and a secrets manager for production.
- Add a secret-scanning tool (e.g. gitleaks, GitHub secret scanning) to CI to block accidental commits of credentials.
- Prefer managed identities / integrated auth over embedded passwords; rotate any secret that has ever appeared in source control or git history.
