### Code Snippet

```csharp
command.CommandText = $"SELECT * FROM USERS WHERE Email = '{email}' AND Password = '{password}';";
```

### Problem Description

The login query compares the supplied `password` directly against a `Password` column (`AND Password = '{password}'`). This implies passwords are stored in the database in **plaintext** (or at best in a reversible/unsalted form), and that authentication is performed by exact string equality inside SQL.

This is a serious credential-management flaw independent of the SQL injection issue:

- **Plaintext storage**: anyone with read access to the `USERS` table — a DBA, a backup file, a second vulnerability such as the SQL injection in the companion report, or a stolen database dump — immediately obtains every user's cleartext password. Because users reuse passwords, this compromises accounts on other systems too.
- **No hashing/salting**: there is no evidence of a slow, salted password hash (bcrypt/scrypt/Argon2/PBKDF2), so even if the column held a simple hash it would be vulnerable to rainbow-table and brute-force attacks.
- **Comparison in SQL**: doing the password check in the `WHERE` clause exposes the comparison to timing/short-circuit behavior and prevents the use of constant-time verification.

## 🛠️ Remediation

### Fixed Code

```csharp
// Look up the user by email only, then verify the password in application code
command.CommandText = "SELECT Id, Email, PasswordHash FROM USERS WHERE Email = @email;";
command.Parameters.Add("@email", SqlDbType.NVarChar, 256).Value = email;

connection.Open();
using var reader = command.ExecuteReader();

if (!reader.Read())
    return Results.Unauthorized();

var storedHash = reader["PasswordHash"].ToString()!;

// PasswordHasher uses a salted, slow algorithm (e.g. ASP.NET Core Identity's
// PasswordHasher<T>, or BCrypt/Argon2) and performs a constant-time comparison.
if (!PasswordHasher.Verify(password, storedHash))
    return Results.Unauthorized();

return Results.Ok(new User(Convert.ToInt32(reader["Id"]), reader["Email"].ToString()!));
```

On registration / password change, store only a salted hash:

```csharp
string hash = PasswordHasher.Hash(plaintextPassword); // bcrypt/Argon2/PBKDF2 with per-user salt
// INSERT/UPDATE USERS SET PasswordHash = @hash ... (parameterized)
```

### Fix Explanation

The fix stops storing and comparing plaintext passwords. The database holds only a **salted, computationally expensive hash** (`PasswordHash`). At login, the app fetches the hash by email and verifies the candidate password using a constant-time `Verify` routine. If the database is later leaked, attackers cannot recover the original passwords without an infeasible brute-force effort per password, and the per-user salt defeats rainbow tables. Verification in application code (rather than in the SQL `WHERE` clause) enables constant-time comparison and avoids leaking match information through query behavior.

### Prevention Best Practices

- Never store passwords in plaintext or with reversible encryption. Use a dedicated password-hashing algorithm (Argon2id, bcrypt, scrypt, or PBKDF2) with a unique per-user salt.
- Use a vetted library such as ASP.NET Core Identity's `PasswordHasher<T>` rather than rolling your own.
- Verify passwords in application code with a constant-time comparison; look users up by a non-secret identifier (email) only.
- Enforce a minimum work factor and review it periodically; add rate limiting and account lockout to slow online guessing.

## 🧪 Proof of Concept (PoC)

### Exploit Steps

1. Obtain read access to the `USERS` table — e.g. via the SQL injection in the companion report, a database backup, or a misconfigured account.
2. Query the table: `SELECT Email, Password FROM USERS;`.
3. Read every user's password in cleartext directly from the `Password` column, then reuse those credentials against this and other services (credential stuffing).

### Malicious Input

```sql
-- via the SQL injection vector, exfiltrate all credentials:
' UNION SELECT NULL, Email, Password FROM USERS --
```
