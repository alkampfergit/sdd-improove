### Problem Description

The `/login` endpoint builds a SQL query by directly interpolating the user-supplied `email` and `password` values into the command text via a C# interpolated string (`$"..."`). No parameterization, escaping, or input validation is performed, so any SQL metacharacters in the input are passed straight to SQL Server and interpreted as part of the query.

Because both `email` and `password` come unfiltered from the HTTP request, an attacker can break out of the string literal and inject arbitrary SQL. This allows authentication bypass, extraction of arbitrary data from any table the connection can read, modification or deletion of data, and—depending on the database account's privileges and SQL Server configuration (e.g. `xp_cmdshell`)—potentially command execution on the host. The connection uses `Integrated Security=true`, so the injected SQL runs with the application's Windows service account privileges, which are often broad. This is the highest-severity issue in the file.

## 🛠️ Remediation

### Fixed Code

```csharp
app.MapPost("/login", (string email, string password) =>
{
    const string connectionString = "Data Source=localhost;Initial Catalog=TestDB;Integrated Security=true;";

    using var connection = new SqlConnection(connectionString);
    using var command = connection.CreateCommand();

    // Use parameterized query - values are sent separately from the SQL text
    command.CommandText = "SELECT Id, Email, PasswordHash FROM USERS WHERE Email = @email;";
    command.Parameters.Add("@email", SqlDbType.NVarChar, 256).Value = email;

    connection.Open();
    using var reader = command.ExecuteReader();

    if (!reader.Read())
        return Results.Unauthorized();

    // Verify the password against a stored hash (see companion report on password handling)
    var storedHash = reader["PasswordHash"].ToString()!;
    if (!PasswordHasher.Verify(password, storedHash))
        return Results.Unauthorized();

    return Results.Ok(new User(Convert.ToInt32(reader["Id"]), reader["Email"].ToString()!));
});
```

### Fix Explanation

The fix replaces string interpolation with a **parameterized query** using `SqlParameter`. With parameters, the SQL text and the user-supplied data travel to SQL Server separately; the data is never parsed as SQL, so injected metacharacters (quotes, `--`, `;`, `OR 1=1`, `UNION`, etc.) are treated as literal string content and cannot alter the query structure. This neutralizes the injection vector entirely. The example also stops selecting `*` and selects only required columns, and moves password checking out of the SQL `WHERE` clause (addressed in the companion report).

### Prevention Best Practices

- Always use parameterized queries / prepared statements (`SqlParameter`, Dapper parameters, or an ORM like EF Core) — never concatenate or interpolate user input into SQL.
- Apply least-privilege to the database account; do not run the app as a high-privilege login and disable dangerous features such as `xp_cmdshell`.
- Add server-side input validation and length limits, and enable a WAF / SQL-injection detection as defense-in-depth.

## 🧪 Proof of Concept (PoC)

### Exploit Steps

1. Send a `POST /login` request and set the `email` parameter to a value that closes the string literal and comments out the rest of the query.
2. The interpolated query becomes `SELECT * FROM USERS WHERE Email = '' OR '1'='1' --' AND Password = '...';`, which returns the first row in `USERS` regardless of credentials.
3. The handler calls `reader.Read()` and returns the first user, achieving authentication bypass. Variants using `UNION SELECT` allow exfiltrating data from other tables.

### Malicious Input

```
email    = ' OR '1'='1' --
password = anything
```
